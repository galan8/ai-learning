# Generate a Software Bill of Materials

## 1. What an SBOM is

A **Software Bill of Materials** is a detailed inventory of every software component used to build a product: open source and proprietary code, libraries, frameworks, and increasingly models and datasets.

The analogy is the food label. You cannot decide whether something is safe to consume without knowing what is in it, and the manufacturer is the only party positioned to tell you.

**The security argument in one line:** when the next Log4Shell lands, the only question that matters is "are we affected, and where?" Without an SBOM that question takes weeks of manual investigation. With one it takes a query.

## 2. Benefits

1. **Better supply chain visibility**, assurance and quality control
2. **Faster identification and remediation** of vulnerabilities
3. **Improved compliance** with regulations and standards
4. **Enhanced risk management** capabilities

## 3. What an SBOM contains

| Element | Why it is there |
| ------- | --------------- |
| **Component name** | Identity |
| **Version** | Determines whether a given CVE applies |
| **Supplier or author** | Who to contact and whose trustworthiness matters |
| **Dependency relationships** | Distinguishes direct from transitive, and shows what pulls in what |
| **Licensing information** | Legal obligation and compatibility |
| **Unique identifiers** | Package URL (purl) or CPE, so components can be matched to vulnerability databases automatically |
| **Hashes and signatures** | Integrity: proves the component is the one described |
| **Metadata** | Timestamps, release dates, author of the SBOM itself |

**A correction to the notes:** hashes and signatures are not "lower receipts"; they are the integrity anchor. A component entry without a hash names something; a component entry with a hash identifies a specific artifact.

**Known vulnerabilities are not part of the SBOM.** The SBOM is an inventory of what is present; vulnerability status is derived by matching that inventory against a vulnerability database at query time. This separation matters, because vulnerability data ages within hours while an inventory stays true until the software changes. Related documents such as **VEX** (Vulnerability Exploitability eXchange) carry the "are we actually affected" judgement.

## 4. The two formats

| | **CycloneDX** | **SPDX** |
| --- | ------------- | -------- |
| **Steward** | OWASP | Linux Foundation |
| **Standard** | Ecosystem standard, also ECMA-424 | ISO/IEC 5962 |
| **Origin focus** | Security first: designed for vulnerability analysis and risk | Licensing and compliance first, now broadened |
| **Strength** | Rich security attributes, VEX support, and BOM types beyond software (ML-BOM, CBOM, SaaSBOM) | Deep licence expression, long standing legal adoption |

**Correction to the notes:** these are two separate, competing standards, not one thing. The notes conflate them. Both are widely supported and most tooling can emit either.

For AI work, **CycloneDX is the more relevant of the two**, because it is the one that defines an ML-BOM.

## 5. Why an SBOM is critical

1. **Perform analysis to evaluate risk** across everything you ship
2. **React quickly when new risks emerge**, because the inventory already exists
3. **Proactive rather than reactive posture**: continuous monitoring against new advisories
4. **Transparency** into both open source and commercial components
5. **Useful to both producers and consumers.** A vendor ships one; a buyer demands one. Increasingly this is contractual rather than optional

## 6. Generating one

The practical answer is a scanner. **Trivy** is the tool used throughout this chapter, and it generates SBOMs for applications, containers, and filesystems in either format:

```bash
# Application dependencies to CycloneDX
trivy fs --format cyclonedx --output app-sbom.json /path/to/project

# The same, in SPDX
trivy fs --format spdx-json --output app-sbom.spdx.json /path/to/project
```

**Where this belongs: in CI, on every build.** An SBOM generated by hand at release time is stale before it is distributed, which is the continuity point from the SCVS lesson.

Other common generators: Syft (Anchore), the CycloneDX language specific tools (`cyclonedx-py`, `cyclonedx-npm`), and SPDX tooling. Storage and analysis is typically **Dependency-Track** (also OWASP), which ingests SBOMs and continuously re-evaluates them against new advisories, which is the piece that turns an inventory into an alerting system.

## 7. Summary

1. An SBOM is a machine readable inventory of everything in a product
2. It contains names, versions, suppliers, dependencies, licences, identifiers and hashes
3. It does not contain vulnerability status; that is derived by matching against a database
4. Two standards: CycloneDX (OWASP, security oriented, supports ML-BOM) and SPDX (Linux Foundation, ISO standard, licensing heritage)
5. Generate with tooling such as Trivy, in CI, on every build
6. Feed SBOMs into something like Dependency-Track so new advisories are matched against existing inventory automatically
